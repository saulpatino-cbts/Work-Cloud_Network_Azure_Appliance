# Changelog

All notable changes to the Cloud Network Assessment Azure Appliance are documented in
this file. Application changes are recorded in the core repository's `CHANGELOG.md`; this file
covers deployment, operations and this repository itself.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- **Images are deployed by digest** (core `TODO.md` → T-701; v1.0 review findings RELEASE-001 / IMG-012). `230-image-update` now requires the core manifest's `digests{}` and composes the pinned reference `docker.io/<ns>/cna:<role>-sha-<7>@sha256:<digest>` for the api, worker, web and migrator images — the tag stays for people and for the web tier's image-update check, the digest is what the platform pulls — and passes all four to `210` (new `migrator_image` input). A manifest without `digests{}` fails the update with a message to rebuild the core first. `210-deploy` refuses any empty or floating (`*-latest`) reference, drops the `migrator-latest` default and the never-working "resolve from the appliance's own build manifest" step, validates every image input with one shared `validate_image_ref` function (pinned accepted, tag-only accepted with a warning, anything else refused), and records the pinned references in the release catalog. Rollback takes `previous_migrator_image` through `workflow_call`; a dispatch rollback resolves the migrator from the catalog record that matches `previous_api_image` (GitHub caps `workflow_dispatch` at ten inputs). `220-fast-redeploy` applies the same validation; `350`/`360` no longer fall back to floating tags when the catalog has no image (they fail instead); `100-validate-prereqs` checks Docker Hub pull access with an authenticated tags listing rather than by pulling `*-latest`. Terraform image variables lose their `example-namespace/*-latest` module defaults and document the pinned form. Shared change — `230`, `resolve_rollback_target.py`, `validate_image_ref` and the `update-available` issue template are byte-identical in the sibling appliance.

### Security
- **Every image is verified against the core's signature and provenance before it is deployed** (core `TODO.md` → T-703; v1.0 review findings RELEASE-003 / IMG-012). The core's `200-build-images` now signs each published digest with cosign (keyless, under its own GitHub Actions OIDC identity) and attaches BuildKit's SLSA v0.2 provenance as a cosign attestation. New shared `scripts/ci/verify_image_signature.sh` runs in `210` on all four images right after the pull-access check, before any plan, and in `220` on every image named: `cosign verify` with the exact certificate identity and issuer, `cosign verify-attestation --type slsaprovenance02`, the attestation subject equal to the digest being deployed, and `predicate.builder.id` under the core repository's `actions/runs/`. The trusted identity is the new repository variable `IMAGE_SIGNING_IDENTITY` (`100` checks it is set) — never the manifest, the dispatch payload or an input — so a tag re-pointed on Docker Hub or an image pushed with the registry credential from anywhere else cannot be rolled out. cosign `v3.1.3` via `sigstore/cosign-installer` (SHA-pinned), the same release the core signs with; the verifier accepts either proof of signing time cosign 3 supports (a Sigstore TSA signed timestamp or Rekor's integrated timestamp), so verification keeps working when Sigstore's signing config moves to Rekor v2. `REVIEW.md` → R-012 records the roll-out order: images built before the core change (including every rollback target recorded so far) do not verify.
- **The web tier authenticates to cna-api with a Terraform-generated token** (v1.0 review findings SEC-001 / ARCH-002). Each workload root generates `CNA_API_TOKEN` (`random_password`, 48 characters), the runtime module stores it as the Key Vault secret `cna-api-token`, and both the api and the web Container Apps receive it as a secret reference — the core's API rejects every request without `Authorization: Bearer <token>` (except `/health` and `/ready`) and refuses to start in appliance mode without it. The api ingress was already internal-only on Azure; the token closes the network-trust assumption itself. **Upgrade order:** apply this release with `210` before letting `230` roll the core images that carry the token check.
- **The api readiness and startup probes use `/ready`** (PY-001 / IMG-011), which runs `SELECT 1` against the database; `/health` stays the liveness probe. A revision with a broken database reference no longer receives traffic.
- **Workflow inputs no longer reach the shell unquoted** (DEVOPS-001, DEVOPS-009). Every `${{ inputs.* }}`, `${{ github.event.* }}`, `${{ steps.*.outputs.* }}`, `${{ vars.* }}` and `${{ env.* }}` that was interpolated into a `run:` block in `000`, `100`, `210`, `220`, `230` and `330` is bound through `env:` and referenced as a quoted variable. `230-image-update` validates the dispatch payload before it can start `210`: the namespace shape, `sha_tag`, and every `images.*` against `^docker\.io/<DOCKERHUB_NAMESPACE>/cna:(api|web|worker|migrator)-sha-[0-9a-f]{7}$` with the tag equal to `<role>-<sha_tag>`; its job permissions are the minimum each job needs. Shared workflow — byte-identical in the AWS sibling.
- **Terraform plan files are no longer uploaded as artifacts** (DEVOPS-002). A saved plan stores variable values in plaintext, so the `tfplan-*` artifacts carried the database admin password, the Entra client secret, the NextAuth secret and the credential-encryption key for anyone with read access. The plan text goes to the step summary; the apply job re-plans and still runs the destructive-plan guard before applying. Past artifacts need deleting and the secrets rotating — `REVIEW.md` → R-006.
- **`340-sync-keys` is removed** (DEVOPS-003). It exported every runtime secret into a downloadable `.env` artifact. Key Vault is the read path.
- **Prod-destroying jobs run under the `hub` environment** (DEVOPS-005). `330-teardown`'s `terraform-destroy` and `cleanup-drift` for `prod` wait for `hub`'s required reviewers; `purge-soft-deleted` and `destroy-backend` stay at repository scope for identity reasons and are gated transitively through `needs` — `REVIEW.md` → R-011.

### Fixed
- **`210`'s two `actions/create-github-app-token` steps are SHA-pinned** (`bcd2ba49…` — v3.2.0, the digest `230` and the AWS appliance already use); they were the only actions in the repository still pinned to a tag, against the `CLAUDE.md` rule.
- **The migration connectivity probe never ran.** Its job manifest pulled the migrator image with `DOCKERHUB_USERNAME` / `DOCKERHUB_PASSWORD`, which no step defined, so the (best-effort) probe job failed to create every time and the step fell through silently. The step now defines both from the same variable and secret the migration job itself uses.
- **`350`/`360` fail when the drift plan itself fails.** Both drift workflows ran `terraform plan -detailed-exitcode ... || EXIT=$?` and then tested only for exit 2, so a plan that *errored* (exit 1 — a missing backend, an expired credential, a provider fault) was read as "no drift" and the job went green. That is the failure mode `TODO.md` → T-105 describes from the other side: the check must be loud before its delivery can be. Exit 0 is still clean and exit 2 still a drift warning; any other exit now fails the job with the plan's own exit code, for both the platform and the workload plan. Mirrors the AWS appliance, whose `350`/`360` were written this way (its `CHANGELOG.md` recorded the sibling gap). Shared workflow change — no other repository is affected; the core owns no drift workflow.
- **The workload storage account's firewall window.** The application storage account has been deny-by-default since `TODO.md` T-106, and `azurerm_storage_account_static_website` is provisioned and refreshed over the data plane, but no workflow allow-listed the runner's IP the way the Key Vault steps do — from any runner not already in `ip_rules`, the workload plan/apply and the portal publish fail with `403` (`AuthorizationFailure`). `210-deploy` (plan and apply), `350`/`360-drift` and `320-publish-portal` now add the runner's public IP before touching the account and remove it in an `always()` step, resolving the account from Terraform state (`storage_account_name` output) rather than restating the naming rule. The first apply of an environment has no account to open, so `210` passes the IP as `TF_VAR_deploy_runner_ip` → workload variable `deploy_runner_ip` → storage module `bootstrap_ip_rules`, which the account is created with; the existing `ignore_changes` on `ip_rules` makes that a creation-time value only. Azure-only wiring (Secrets Manager and S3 have no equivalent), so nothing changes in the sibling.
